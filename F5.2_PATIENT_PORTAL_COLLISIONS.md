## 1. Direct Collision: Duplicate "appointments" Entry

### The Issue

**Both F5.2-imp and F1-Appointments add the same SERVICE_MAP entry:**

```python
# F1-Appointments adds:
"appointments": os.environ.get("REFERRAL_SERVICE_URL", "http://localhost:8003"),

# F5.2-imp adds:
"appointments": os.environ.get("REFERRAL_SERVICE_URL", "http://localhost:8003"),
```

### Why It Happens

- **F1**: Appointments is a new feature; needs to route `/api/appointments/*` to Referral Service (8003)
- **F5.2**: Patient Portal includes appointment viewing; adds the same entry to route patient portal appointment requests

Both teams independently decided to add the same route to the gateway.

### Merge Conflict

When merging both branches to master:

```
F5.2-imp: +"appointments": 8003
F1-Appointments: +"appointments": 8003  ← CONFLICT: same key, same value
```

Git will flag this as a conflict in `gateway/main.py` because both branches modify the same line in SERVICE_MAP.

### Resolution

**Simple**: Accept either version (they're identical). The merge conflict is a **false positive** — both branches want the same thing.

**Recommended merge strategy**:
```bash
git merge F1-Appointments  # Adds "appointments"
git merge F5.2-imp         # Detects conflict; resolve by keeping the "appointments" entry (already there)
```

Or vice versa — order doesn't matter since the entries are identical.

### Risk Level

🟡 **LOW** — Not a functional collision, just a duplicate change that needs conflict resolution during merge.

## 2. Indirect Risk: Cross-Feature Dependencies

### Patient Portal Data Dependencies

The Patient Portal needs to display:

1. **Referral & Appointment Data** (from Referral Service 8003) ✅
   - Already in gateway SERVICE_MAP
   - F5.2 has no collision here

2. **Lab Results** (from Lab Service 8006) ⚠️
   - F3 (Lab) adds `"labs": 8006` with `UNPREFIXED_SERVICES` path logic
   - Patient Portal may request lab data for referral details
   - **Risk**: If Lab's proxy logic fails, portal can't display lab results

3. **Pharmacy Prescriptions** (from Pharmacy Service 8006/8007) ⚠️
   - F4 (Pharmacy) adds `"pharmacy"` with different path-stripping logic
   - Patient Portal may request prescription data for patient dashboard
   - **Risk**: If Pharmacy's proxy logic fails OR port conflict (8006 vs 8007), portal can't display prescriptions

4. **Insurance Status** (from Patient Service 8001) ✅
   - F2 (Insurance) uses existing `patients` route
   - Patient Portal can display insurance status
   - No collision here

### Dependency Chain

```
Patient Portal (F5.2)
├─ Referral Service (8003) ✅ Established
├─ Lab Service (8006) ⚠️ Depends on F3's proxy logic
├─ Pharmacy Service (8006 or 8007) ⚠️ Depends on F4 port decision + proxy logic
└─ Patient Service (8001) ✅ Uses existing route
```

### What Could Go Wrong

If F3 and F4 fail to merge cleanly:

1. **Lab proxy logic lost**: `/api/labs/*` requests fail → Lab panel in portal shows 404
2. **Pharmacy proxy logic lost**: `/api/pharmacy/*` requests fail → Pharmacy panel in portal shows 404
3. **Port conflict unresolved**: Only one of Lab/Pharmacy works → Incomplete data in portal

### Mitigation

✅ **For us (F5.2)**:
- Ensure Patient Portal's HTTP client gracefully handles 404 errors from Lab/Pharmacy
- Show "Data unavailable" message instead of breaking
- Don't hard-require Lab/Pharmacy data for portal to function

✅ **For other teams** (coordination):
- Resolve Lab/Pharmacy port conflict before merging (8006 vs 8007)
- Ensure merged proxy logic handles both UNPREFIXED_SERVICES and pharmacy routing
- Test portal can reach both services through gateway
